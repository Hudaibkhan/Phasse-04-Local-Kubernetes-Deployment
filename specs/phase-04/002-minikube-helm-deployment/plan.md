## Summary

Deploy Evolution Todo application (frontend + backend) to Minikube using existing Helm charts. Update chart templates and values to match Docker images built in Phase IV Docker Foundation (001). Configure Kubernetes Deployments, Services, Secrets, and ConfigMaps for local cluster deployment. Verify all Phase III features (authentication, task CRUD, chatbot) work in Kubernetes environment.

**Technical Approach**: Update existing Helm chart in `todo-app/` directory with proper image references, port configurations, environment variables, and health checks. Deploy to Minikube using `helm upgrade --install` command. Verify deployment using kubectl and test application access via Minikube service URLs.

## Key Design Decisions

### 1. Single Helm Chart with Multiple Deployments

**Decision**: Use one Helm chart (`todo-app`) with separate deployment templates for frontend and backend.

**Rationale**:
- Simplifies deployment (single `helm upgrade --install` command)
- Maintains logical grouping of related services
- Easier version management and rollback
- Follows Helm best practices for multi-tier applications

**Alternatives Considered**:
- Separate charts for frontend/backend: Rejected due to deployment complexity and version coordination issues
- Umbrella chart with subcharts: Rejected as overkill for two simple services

### 2. NodePort for Frontend, ClusterIP for Backend

**Decision**: Frontend uses NodePort service type, backend uses ClusterIP.

**Rationale**:
- Frontend needs external access for users (NodePort works with Minikube)
- Backend only needs internal cluster access (ClusterIP is more secure)
- Minikube doesn't support LoadBalancer without additional setup
- NodePort is simpler than Ingress for local development

**Alternatives Considered**:
- LoadBalancer for frontend: Rejected due to Minikube limitations
- Ingress controller: Rejected as unnecessary complexity for local deployment

### 3. Manual Secret Creation (Not Helm-Managed)

**Decision**: Secrets created manually with `kubectl create secret` before Helm deployment.

**Rationale**:
- Prevents accidental commit of sensitive data in values.yaml
- Follows Kubernetes security best practices
- Secrets persist across Helm upgrades/rollbacks
- Clear separation between infrastructure (Helm) and secrets (kubectl)

**Alternatives Considered**:
- Secrets in values.yaml: Rejected due to security risk
- External secret management (Vault, Sealed Secrets): Rejected as overkill for local development

### 4. Image Loading Strategy

**Decision**: Use `minikube image load` to load Docker images into Minikube.

**Rationale**:
- Images already built locally from Docker Foundation (001)
- No need for external registry for local development
- Faster than pushing/pulling from registry
- Works offline

**Alternatives Considered**:
- Local Docker registry: Rejected as unnecessary complexity
- Pull from Docker Hub: Rejected as images are local-only

### 5. Health Check Configuration

**Decision**: Match Docker health checks in Kubernetes probes.

**Rationale**:
- Consistency between Docker and Kubernetes environments
- Health checks already proven working in Docker containers
- Backend: GET /api/health (30s interval, 40s startup)
- Frontend: GET / (30s interval, 20s startup)

**Alternatives Considered**:
- TCP socket probes: Rejected as less informative than HTTP probes
- Exec probes: Rejected as HTTP probes are simpler and sufficient
